# How the Regexp/FST Input Files Are Generated and Their Relationship to Database Tables

## Overview

The system generates finite-state transducer (FST) regex files for Georgian morphological analysis. The process has two main branches -- **verbs** and **nouns** -- each combining hand-written morphological rules (transducer definitions) with lexical data pulled from a PostgreSQL database (`gnc`), in the schema `morph`.

## Database Tables

The key database tables (all in the `morph` schema) are:

### `morph.verb_features`

The central verb table. Each row represents one morphological feature configuration for a verb root. Columns include: `unique_id`, `id`, `sub_id`, `root`, `c_root` (citation root), `tense` (pipe-delimited list like `|present|future|`), `gv` (Grundverb class: T1, P1, IV1, etc.), `sf`, `caus_sf`, `vv` (version vowel), `tsch_class`, `morph_type` (active/passive/causative), `passive_sfx`, `type_aorist`, `type_obj_3_pfx`, `type_aorist_3sg`, `type_optative`, `subj_pers`, `obj_pers`, `style`, `lang`, `paradigm_replacement`, and many more morphophonological type-features.

### `morph.verb_paradigm`

Links a verb ID/sub-ID to its preverbs (`pv`, `impf_pv`, `pf_pv`, `pf_12_pv`), citation root (`c_root`), verbal nouns (`vn`, `impf_vn`, `pf_vn`), Tschenkeli class, `features_sub_id` (the sub-ID whose features to use), and `base_sub_id` (for alternations like active/passive pairs).

### `morph.participle`

Stores participle stems (masdar, past/present/future/negative participles) with `id`, `sub_id`, `type`, `stem`, `code` (declension class), `variety` (language/dialect), `aspect`, and `main_form`.

### `morph.xle_template`

Maps `(id, sub_id)` to XLE grammar template strings (syntactic frames).

### `morph.noun_features`

Noun/adjective/proper-name stems with columns: `stem`, `code` (declension class: A, B, C, H, etc.), `pos`, `features` (like `+Name`, `+Anim`), `style_features`, `lang`, `translation`.

### `morph.verb_translation`

Stores translations and links sub-paradigms (`base_sub_id`).

### `morph.related_verbal_nouns`

Links related verbal nouns for the same verb ID.

### `morph.pv_variant`

Preverb variant mappings.

### `morph.fullform`

Attested full forms with corpus counts (used for disambiguation).

## The Three Types of Generated Regex Files

### 1. Verb Morphology Regex (`verb.regex`)

Generated by **`write-verb-regex-file()`** (`utp-to-fst.lisp:790`). This works by splicing:

- It reads `verb-splice.regex` as a template, which contains the hand-written morphological rules (tense suffixes, screeve signs, phonotactics, etc.).
- At a marker line (`# <--- automatically generated code will be inserted here --->`), it inserts code generated by loading `verb-transducer.lisp`.
- `verb-transducer.lisp` defines the morphological transducer rules using the `#[name = ...]` and `precompile-u-transducer` macros -- preverb groups, prefix groups (subject/object person markers), suffix groups for each tense series (present, aorist, perfect), enclitics, etc. These are **purely rule-based**, not database-driven.

### 2. Verb Lexicon Regex (`finite-root-list0..7.regex`)

Generated by **`write-verb-lexicon-regexp()`** (`utp-to-fst.lisp:615`). This is **directly database-driven**:

- **`fetch-id-roots()`** queries `morph.verb_features` to build `*id-to-roots-table*` (mapping ID → root list) and `*id-to-c-root-table*` (ID → citation root).
- For each verb ID, **`verb-lexicon-regexp()`** calls **`get-root-override-features()`** (`verb-feature-table-sql.lisp:565`), which runs a large SQL query joining `verb_paradigm`, `verb_features`, `participle` (for masdar), and `xle_template`. This returns all morphological features per root.
- These features are combined with templates from `feature-templates.lisp` (`feature-template()` + `morph-tense-template()`) to produce a complete feature specification for each tense of each root.
- The output is foma/fst regex format: each root becomes an entry like `{vn/root}:{root} "@U.VClass.T1@" "@U.Tense.Present@" ...` using flag diacritics (`@U.`, `@R.`, `@D.`) to encode features.
- The roots are partitioned across 8 files (`finite-root-list0.regex` through `7.regex`) for parallel compilation.

### 3. Noun Stem Regex (`noun-list0..7.regex`, participle lists, geonames)

Generated by **`write-fst-noun-stems-sql()`** (`noun-table-www.lisp:918`):

- Queries `morph.noun_features` for all noun/adjective stems with their declension codes, POS, features, and style.
- For each stem, calls `write-stem()` which generates a regex entry encoding the stem with flag diacritics for: `Cat` (category), `SubCat`, `StemType` (based on declension code: consonant, vowel-ა, vowel-ე, etc.), `SyncStem`, `RigidStem`, `Style`, `Lang`.
- Also partitioned across 8 files for parallel compilation.

**`write-fst-participle-stems-sql()`** (`noun-table-www.lisp:1217`):

- Queries `verb_paradigm` joined with `participle`, `verb_features`, and `xle_template` to get all participle/masdar stems.
- Generates separate regex files: `masdar-list.regex`, `past-part-list.regex`, `present-part-list.regex`, `future-part-list.regex`, `negative-part-list.regex`.
- Each entry encodes the participle stem along with its verbal noun (lemma), preverb, and root type.

**`write-fst-geo-stems()`** and **`write-fst-extracted-stems()`** handle geographic names and extracted productive forms (like words ending in -ობრივი, -იზაცია, etc.).

### Noun Morphology Regex (`noun.regex`)

Generated by **`write-noun-regex-file()`** (`utp-to-fst.lisp:758`). Similar splice pattern:

- Reads `noun-splice.regex` as template (which loads the pre-compiled noun stem FSTs and defines `NounStem`).
- Inserts code from `noun-transducer.lisp` at the marker -- this defines the case/number declension rules (nominative, ergative, dative, genitive, instrumental, adverbial, vocative groups), plural formation, old plural, double declension, enclitics, postpositions, etc.

## The Assembly Pipeline (`compile-morphology`)

The master function **`compile-morphology()`** (`utp-to-fst.lisp:877`) orchestrates everything:

1. Writes `verb.regex`, `noun.regex`, `noun-guessed.regex` (spliced rule files)
2. Writes geographic name stems
3. Writes participle stem lists (masdar, past/present/future/negative participles) from DB
4. Fetches verb ID/root mappings from DB, writes `finite-root-list0..7.regex`
5. Writes noun stem lists from DB (`noun-list0..7.regex`)
6. Compiles all `.regex` files into `.fst` binaries using the `fst` (or `foma`) tool, running up to 8 threads in parallel
7. Assembles everything into final transducers via `syntax.regex`

## Data Flow Summary

```
PostgreSQL (morph schema)
    │
    ├── verb_features + verb_paradigm + participle + xle_template
    │       │
    │       ├──> finite-root-list0..7.regex  (verb roots + features as flag diacritics)
    │       └──> masdar/past-part/present-part/future-part/negative-part-list.regex
    │
    ├── noun_features
    │       └──> noun-list0..7.regex  (noun stems + features)
    │
    └── (geonames, extracted forms)
            └──> geonames-list.regex, extracted-noun-adj.regex

Hand-written rules (Lisp transducer definitions)
    │
    ├── verb-transducer.lisp ──splice──> verb.regex
    └── noun-transducer.lisp ──splice──> noun.regex

All compiled by fst/foma ──> syntax.regex ──> final .fst binaries
```

The database holds the **lexicon** (roots, stems, and their morphological properties), while the Lisp transducer definitions encode the **morphological rules** (how prefixes, suffixes, screeve signs, and person markers combine). The regex files are the meeting point where lexical entries (from DB) are dressed with flag diacritics that the morphological rules (from the transducers) can check during analysis/generation.
